Data protection

My research and current independent work focus on how personal data is collected and protected in Africa, and on Rwanda's data protection law, Law N° 058/2021.

  • Published, 2025

    Cookie consent and data protection law across Africa

    Co-authored an ACM COMPASS paper analysing 1,793 websites in 49 countries against 37 national data protection laws. 78% of sites set cookies, only 17% asked for consent, and none of the laws set specific cookie opt-in rules for websites. Coverage by CMU Engineering.

  • In progress

    Measuring Rwandan websites against Law N° 058/2021

    An independent measurement study I designed. Data is collected passively in a browser that never accepts cookies. Privacy notices are coded with local AI models, checked against human coders. The ethics approach follows the Menlo Report. Data collection is under way, with a preprint expected in early 2027.

  • Draft, in pilot

    Law N° 058/2021 readiness self-assessment

    A 17-question scored self-assessment that helps an organisation see where it stands against Rwanda's data protection law. Currently being piloted with a few organisations.

  • Built

    Data protection compliance service kit

    Built a compliance service kit: a gap assessment checklist, risk register, assessment report and privacy notice templates.

The SOC homelab

A segmented attack-and-detect environment I built to reproduce real techniques, check whether my detections actually fire, and write up the gaps honestly.

  • Proxmox host with segmented security zones routed through OPNsense, keeping attack tooling separate from monitored targets.
  • Suricata and Wazuh caught the same Hydra brute force from two angles: the network and the host.
  • Custom rule 100101 flags a successful SSH login after repeated failures. It was validated against real log lines with wazuh-logtest before it was trusted.
  • Findings are labelled observed or detected. A technique counts as covered only when an alert fires, not when traffic merely shows up in a log.

What happens when an attacker writes instructions into an SSH username?

The lab's offline AI triage agent reads attacker-controlled alert fields, so I attacked it. The first version didn't pass. This is the pipeline, and where it is defended.

  1. Attack

    Kali + Hydra

    SSH brute force against an Ubuntu target, ending in a successful login.

  2. Detection

    Wazuh rule 100101

    Five or more failed SSH logins, then a success from the same IP within 120 seconds. Fires at level 12.

  3. Untrusted input

    Crafted alerts

    Adversarial alert samples hide instructions in the username, source IP and log message fields.

  4. Model reads it

    Local LLM agent

    qwen3:4b on Ollama, offline. It advises only: it cannot block IPs, disable accounts or change severity.

  5. Contained

    Python guardrails

    Severity computed in code. An injection tripwire and a recommendation sanitiser catch what the model lets through.

The injection never downgraded a level-12 alert. A test run against three OWASP LLM risk categories still exposed two gaps: a schema-manipulation attempt went undetected, and a prompt-extraction attempt leaked into a recommendation. Both are fixed and covered by regression tests in GitHub Actions. Read the write-up.
